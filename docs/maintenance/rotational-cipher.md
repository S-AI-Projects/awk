# Maintenance Guide: Rotational Cipher (`rotational-cipher`)

## 1. Problem Formulation & Specification

The Rotational Cipher (also known as the Caesar Cipher) shifts Latin alphabetic characters by an integer key $k \in [0, 26]$:

$$c = \begin{cases} 
(p - \text{'a'} + k) \bmod 26 + \text{'a'}, & p \in [\text{'a'}, \text{'z'}] \\
(p - \text{'A'} + k) \bmod 26 + \text{'A'}, & p \in [\text{'A'}, \text{'Z'}] \\
p, & \text{otherwise}
\end{cases}$$

- Punctuation, digits, whitespace, and non-alphabetic symbols pass through unchanged.
- Case is strictly preserved.
- The rotation key is supplied via `-v distance=<k>`.

## 2. File Organization & Runner Architecture

The test runner (`bin/validate_one_exercise`) does not guess file locations using heuristics. Instead, it inspects `exercises/practice/rotational-cipher/.meta/config.json`:

```json
{
  "authors": [
    "IsaacG"
  ],
  "files": {
    "solution": [
      "rotational-cipher.awk"
    ],
    "test": [
      "test-rotational-cipher.bats"
    ],
    "example": [
      ".meta/example.awk"
    ]
  },
  "blurb": "Create an implementation of the rotational cipher, also sometimes called the Caesar cipher.",
  "source": "Wikipedia",
  "source_url": "https://en.wikipedia.org/wiki/Caesar_cipher"
}
```

### 2.1 How the Runner Finds Test and Solution Files
In `bin/validate_one_exercise`:
1. **Directory Context**: The runner changes directory into `exercises/practice/rotational-cipher`.
2. **Metadata Ingestion**: The runner queries `.meta/config.json` using `jq`:
   - `stub=$(jq -r '.files.solution[0]' "$config")` $\to$ `rotational-cipher.awk`
   - `tests=$(jq -r '.files.test[0]' "$config")` $\to$ `test-rotational-cipher.bats`
   - `solution=$(jq -r '.files.example[0] // .files.exemplar[0]' "$config")` $\to$ `.meta/example.awk`
3. **Execution Harness**:
   - The runner creates an isolated temporary directory.
   - It copies the reference solution (`.meta/example.awk`) into the stub path (`rotational-cipher.awk`).
   - It executes `bats "${tests}"`.

## 3. Metadata Verification & Security Contract

To ensure track integrity and prevent path traversal vulnerabilities, all declared files in `config.json` must adhere to strict resolution rules:
1. **Schema Parsing**: Parse the `.files` dictionary directly for keys `solution`, `test`, `example`, and optional `editor`.
2. **Path Containment & Traversal Rejection**: Every path must resolve within the exercise directory. Any path containing parent directory traversal (`..`), absolute paths, or symlinks escaping the exercise root must be rejected with an error.
3. **Existence Verification**: Every declared file must exist as a regular file.

### 3.1 Failure Fixture Matrix

The verification script `work/R06-T038/check.py` validates the metadata validator against three synthetic fixtures:

| Fixture Name | Injected Fault | Expected Outcome |
|:---|:---|:---|
| **Real Metadata** | None (`config.json` as authored) | Validation succeeds (0 errors). |
| **`missing-reference`** | `example: [".meta/nonexistent_example.awk"]` | Rejection: Declared example file does not exist. |
| **`missing-test`** | `test: ["missing-test.bats"]` | Rejection: Declared test file does not exist. |
| **`outside-exercise`** | `solution: ["../../bin/pr"]` | Rejection: Path traversal outside exercise boundary detected. |

## 4. Test Suite Baseline

The test suite consists of 10 canonical test cases, anchored on:
- `rotate a by 0, same output as input` (`-v distance=0 <<< "a"` $\to$ `"a"`)
- `rotate a by 1` (`-v distance=1 <<< "a"` $\to$ `"b"`)
- `rotate a by 26, same output as input` (`-v distance=26 <<< "a"` $\to$ `"a"`)

All 10 tests pass against the reference implementation `.meta/example.awk`.
